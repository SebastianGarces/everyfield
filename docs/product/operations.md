# Administration and operations

ADM-001–007 and OPS-001–011 preserve feedback intake/status, authorized administration, dashboard/public surfaces and safe engineering operation. The platform administrator is an explicit immutable-principal grant, distinct from plant/organization Owner/Admin. No email allowlist, CRM title, model instruction or feedback text creates that authority. Operational actions are scoped internal capabilities; no general customer audit/recovery console is added.

## Private intake and public feedback

ADM-001 follows the design feedback dialog. It collects category, description, page, address, church, role, browser, screen size, theme, app version and time. Category is bug/suggestion/question/other and description is trimmed to 1–5,000 characters. Page is its displayed label; address is the internal path, stripped of query, fragment and tokens. Church and role come from trusted current account context; unavailable details stay null. Store the private original, immutable author, occurrence/idempotency key and trusted submission time durably; success means stored, not published/implemented. Canonicalize page location to known internal route label, strip query/fragment/tokens and never preserve arbitrary external credentials in outward fields. Native own list/status uses authenticated original account, bounded cursor/25 rows and a dedicated `FeedbackOwnStatus`: feedbackId, submitted category/date, current triage state, publication state and approved public URL/issue number when present. It excludes private originals/admin joins, submitter/contact/plant IDs, internal notes, agent routing or private logs. `FeedbackIntakeReceipt` returns feedbackId/submittedAt/stored plus current triage/publication state; external unknown is a factual publication state rather than false intake failure. Foreign/gone/suspended author fails closed. Church, role, browser, screen size, theme and app version stay in the private original and never appear in a public issue, including reviewed richer text. No screenshot or attachment is collected, and no public roadmap is required.

ADM-002 platform triage list filters status/category with bounded pagination and uses scoped private projection only after immutable platform grant check. Status is new/reviewed/resolved/dismissed, with expected revision, actual actor/time and correction/no-op history; unknown feedback fails not-found. Closing a public issue is an observed external issue fact and does not silently set implemented/resolved/deployed in EveryField. A plant/org Admin does not become platform triager or receive private original access by affiliation.

ADM-003 automatically creates and triages safe issues in a **separate PUBLIC feedback repository**, while preserving private originals. Frozen publication payload and actual destination `(repository numeric/node ID, owner/name snapshot, issue number/node ID, URL)` survive configuration/rename changes; an old issue locator cannot be rebuilt from today's global repo string. The owner-provided merged development workflow will govern implementation/escalation and human-reviewed PR routing. Its merged source/version is received and recorded in G-WORKFLOW, with reconciliation still required; no competing rubric, autonomous coding class, other-worktree inspection, automatic merge or deployment is invented.

The initial safe publisher is a deterministic closed serializer. It uses only validated category, a public product-area label from an approved route allowlist, fixed wording describing a product report, and an opaque random publication-occurrence marker. Example: title “Bug report — Documents”; body “A product bug report was submitted for Documents. Private details are retained for authorized triage. Reference: <opaque marker>.” Public output contains no raw title/description/URL/query, internal user/plant IDs, names/contact details, screenshots/logs, private care/body/metadata or attachments. Church, role, browser, screen size, theme and app version stay in the private original and never appear in a public issue, including reviewed richer text. Private route variants map to a generic Application label; no record-existence label. User input is data, never tool instructions. Safe normal serialization publishes automatically without requiring manual approval. Malformed/unknown safe fields or uncertain sanitization keeps intake private and publication held; there is no raw fallback.

This minimal public summary omits the detailed private bug narrative. Authorized triage may resolve the private original through its opaque locator only under the merged owner workflow and actual platform grant, separately from public issue/model context. Optional richer text/otherwise-withheld material requires review of the exact payload, public audience and provenance. An Evry-created feedback submission is itself an exactly reviewed durable write; the named automatic publisher does not grant general assistant autonomy. No model/classifier guarantee or blanket consent is selected.

Publication state is pending/held/publishing/published/rejected/unknown, with immutable intended payload hash/destination and bounded job receipt. Commit intent before external call; 10-second provider timeout. A lost issue response enters unknown and reconciles the frozen opaque marker in the exact stored repository before another create. GitHub does not gain an invented exactly-once guarantee: authoritative absent evidence plus bounded retry permits retry; inaccessible/ambiguous marker search remains held unknown and operator resolves in the actual repository. Duplicate issue candidates require review, not new publication. Triage labels/actions are recorded as actual receipts; issue creation/closure never claims PR merge or implementation. Optional operator email uses the shared mail ledger, safe content and configured authorized recipient; false/unknown transport result remains visible.

## Operating and approval gates

Development uses suitable existing free allowances. [Execution and illustrative cost envelope](../architecture/execution.md#usage-and-cost-envelope) contains low/expected/high assumptions, monthly vendor costs, recovery storage/drill/model retries and operator load. The selected vendors and backup destination do not authorize paid plans, spending, repository creation, credentials, provider configuration, actual backup/restore or deployment.

Design closes with finite contracts, chosen executor/backup isolation, exact fields/ownership, failure states and named fixtures. Implementation closes later with actual SQL/browser/provider/settings/restore evidence. Before real customer data, actual cost approval, sufficient invocation/recovery settings, fresh encrypted daily backup, recoverable key access, credential exclusion, provider expiry and coherent restore demonstration are required. Reconciliation of the received merged development workflow remains the routing blocker; concrete account/repository/maintenance-host identity are execution inputs and authorization, not new product-policy questions.
