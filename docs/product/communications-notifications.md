# Communications and notifications

This is the operative target for COM-001–010/012 and NTF-001–015. The contact-evidence producer for COM-011 is [Meetings and follow-up](meetings-follow-up.md). Native UI and Evry call the same domain operations. Every durable Evry effect has exact human review; automatic named system producers execute only their committed purpose and scope.

## Mail contract

The communication aggregate owns composition, frozen audience, draft/history and linked Person/meeting projections. `email_intent` owns the single logical outgoing effect; `email_attempt` owns attempts and external receipts. Inbox read state belongs to `inbox_entry`. Notifications, bulk communication, security mail, Discovery receipts and public invite requests use this same transport. A notification delivery table or communication status must not become a second competing provider ledger.

An intent has immutable ID, typed account/plant/exact-organization subject, purpose, initiating operation/receipt, recipient account or same-plant Person reference, normalized address snapshot, sanitized per-recipient HTML/plain text, payload hash and optional scheduled Instant. Secret tokens are encrypted operational payload, excluded from ordinary audit/model/log projections. One recipient intent is unique per logical occurrence/purpose/recipient. Attempt records preserve immutable request identity/hash, firstDispatchedAt, provider key, ordered batch intent IDs and each member's batch index; no new batch table is needed. A batch has one exact ownership/projection scope; account-private/security mail is singleton unless every member demonstrably shares the same permitted scope. Protected internal batch manifests never leak other accounts/tenants through an authorized recipient receipt. A single-send key derives from its immutable request/intent identity. Resend batch has one key for the complete frozen API request, derived from the immutable ordered manifest/request identity; individual recipient outcomes retain that request key and index. Retry of unknown whole-batch acceptance uses the identical frozen request/key, not a regrouped subset. Confirmed-refused members alone may get a separately recorded safe retry request. No key derives from mutable subject, INSERT RETURNING order or current time.

The domain transaction saves reviewed communication, exact selected membership, recipient/address exclusions, required mail intents, domain history, audit and command receipt together. Provider calls occur outside the transaction. Replay returns that original receipt; the same review cannot create another send. At handoff recheck subject active state, current actor/authority, recipient relationship, source revision, email reachability and global suppression. An unreviewed change to content, audience, addresses, attachments or time invalidates the approval.

| State/fact | Meaning and permitted transition |
|---|---|
| draft | Saved incomplete composition; no mail intent or provider effect. |
| pending | Committed authorized outgoing intent, waiting for a bounded claim. |
| dispatching | Claimed with generation/lease; no assertion that provider accepted. |
| accepted / scheduled | A provider receipt identifies acceptance, and scheduled time when relevant; neither proves sent or delivered. |
| rejected | Confirmed refusal; retain permanent versus retryable reason without raw provider payload. |
| unknown | Request may have been accepted but authoritative result is absent; reconcile, never blind fresh-key resend. |
| sent / delivered / bounced / complained | Independent provider facts, event time and receipt time retained. Engagement open/click is separate and is not proof of human attention. |
| cancellation_requested / cancelled | Request is not confirmation; confirmed provider cancellation alone permits replacement. Sent or unknown races remain explicit. |

Monotonic projections preserve stronger successful engagement facts and terminal hard-bounce/complaint facts without discarding event history. A late accepted event cannot regress delivered; a soft bounce never becomes a fabricated hard bounce. A partial batch exposes accepted/rejected/unknown counts individually. A zero-accepted confirmed rejection fails both compose and resend with the saved communication ID. An all-unknown batch reports unknown, with no success claim.

Use a 10-second transport timeout, batches of at most 100, and three safe retry attempts at 5 minutes, 10 minutes and 20 minutes for confirmed retryable refusal. Honor longer provider Retry-After within the existing job. Uncertain acceptance enters reconciliation immediately. [Resend idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys) currently retains request keys for 24 hours and supports the email/batch endpoints. Persist firstDispatchedAt before the first request and conservatively stop automatic identical-key replay at firstDispatchedAt+23 hours 55 minutes; retries never restart that clock. Inside that bound the identical frozen request may be replayed with the same key after current checks. Afterward lack of authoritative negative evidence blocks automatic replay. Operator recovery links actual provider ID/console evidence or leaves unknown. Resend is a separate reviewed business decision/new identity, not recovery of an unknown attempt. Verify actual documented key behavior before use.

Signed webhook handling verifies raw body, signature and timestamp before lookup, durably inserts unique provider event ID plus processing state before 2xx, then applies facts idempotently. Storage failure returns retryable non-2xx. A valid event with an unknown message ID is safely stored/acknowledged for reconciliation; it is not a public tenant selector. Event-time facts and receipt-time processing are distinct. Suppression records use normalized address, hard-bounce/complaint reason and attributed clear history; current self-address restoration uses fresh native identity proof, a reason and explicit review. Security/invitation mail ignores optional category toggles but still respects its purpose, token secrecy and address safety. Suppression restoration cannot grant another account's address or resurrect canceled sends.

## Drafts and provider scheduling

Save incomplete drafts without send validation or intent. At review render the exact recipients, sanitized per-recipient payload, exclusions and resolved church-local time/Instant. A fold/gap requires the established explicit date/time choice; display local zone and ISO handoff consistently. Schedule via Resend API within its documented 30-day window, including its supported batch operation. There is no SMTP or application-held long-horizon scheduler. [Resend scheduling](https://resend.com/docs/dashboard/emails/schedule-email) documents API time updates and cancellation.

After acceptance, a reviewed time-only reschedule targets the stored provider IDs and leaves audience/content immutable. Any body/audience replacement requests cancellation of every affected old accepted intent, records actual outcomes, and creates replacement only after all relevant old cancellations are confirmed. Unknown, already-sent or partial cancellation blocks automatic replacement; UI presents exact affected recipients and options. Material subject/authority/address/suppression/deletion changes request provider cancellation and reconciliation. The app reauthorizes at handoff and cannot promise an application check at the later provider-send instant. Deletion cancellation never reinstates canceled email. Draft/schedule/sent/delivery and read/task-completion remain separate.

## Notification product

One inbox/bell, one email channel and one preferences page cover actual producers. Ordinary eligible category/channel defaults are ON. Planter digest defaults email ON/in-app OFF, weekly Sunday 16:00 church-local, with a daily option; no duplicate inbox digest by default. Exact-organization oversight defaults daily relevant activity and allows daily/weekly frequency and channel choices. Absence inherits default; explicit choice is persisted even when equal to default and survives audience changes. A cadence save cannot overwrite an unrelated explicit channel choice. Preferences never enlarge audience. Password/security/invitation purpose mail is separate.

Domain reminder/relationship/phase producers remain their domain owners. Existing Evry adapters WP-071/072/081/082 reuse these exact predicates/review projections. Later proof includes concurrent reviewed replay, dropped provider acceptance response, malformed/short batch response, webhook storage outage/out-of-order replay, revoked audience, material scheduled-email cancellation race, explicit preference survival, DST periods and multi-day catch-up without tail starvation.
