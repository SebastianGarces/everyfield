## Implementation conclusions

1. Bulk communication and notification delivery implement related transport concerns twice. Notification delivery has durable channel claims, suppression, preference checks, retry policy, grouping and provider idempotency; raw bulk sends lack several of those. Keep the two different product workflows, share one transport/reconciliation adapter and explicit delivery attempt contract.
2. Alpha corrects zero provider acceptance and normal compose feedback. It does not make delivery transactionally durable, and resend action still does not inspect a failed result. Treat alpha behavior as mandatory parity input, not merged main.
3. Wiki read/navigation/search/progress/bookmark/rating/export functionality is real. Current content-admin mutations were deliberately removed. The corpus is database-resident, but a verified prior published-global snapshot is now available: 96 articles, 21 sections and 7 message templates at alpha2107, SHA256 `7933b93d693b73b3d8768aa2f7e2ad91fa665b6ec23127cb8b4856466d936f59`. A new live export is unnecessary for planning; source currentness and SME editorial approval remain required before bootstrap. MDX syntax success is not semantic approval.
4. Eleven static document templates produce twelve template/format combinations. Exact-byte preview is valuable; generated bytes are privately stored with church-scoped re-download. Generation currently uses a mutating GET and weakly bounded merge values; preserve outcomes with a typed POST and separately authorized preview.
5. Notification category labels, unused team mail helpers and FRD assertions do not establish running producers. Missing communication alerts, team health/training producers and planter assessment-ready producer are explicit decisions/gaps, not quietly dropped capabilities.
6. Platform admin currently means an email allowlist. Feedback is durable but external bridge publication is best effort, exposes free descriptions to its configured GitHub destination, and lacks durable dedupe/retry. A fresh project should use explicit platform-principal grants and reviewed external publication defaults.

## Contracts to freeze before parallel implementation

- `AuthorizedActor` carries immutable principal ID, tenant relationship/capabilities, request correlation and approval reference; services resolve current permission rather than accepting agent-provided roles.
- `ReviewedCommunication` carries message/template/content version, sanitized HTML/plain text, resolved fields, exact recipient IDs/address snapshots, consent category, provider idempotency key and preview checksum. Review expires on audience/content change; execution rechecks reachability and suppression.
- `DeliveryIntent` and `DeliveryAttempt` distinguish provider acceptance, confirmed delivery, engagement, permanent refusal, transient refusal and unknown external outcome. Retries reuse the correct provider key; they do not turn an ambiguous send into a fresh send. Webhook inbox stores provider event ID, event time and processing status before acknowledgement.
- `NotificationAnchor` is a typed discriminated church/sending-church/network identity, with real entity FKs or exact constrained ownership repository; no generic UUID that merely happens to refer to an organization. Category policy and audience sharing gate are centralized data, not scattered role strings.
- `ReferenceBundle` contains canonical source/version/approval/checksum, immutable article/template IDs, exact slug/link topology, approved rubric/playbook pointers, and deterministic install/upgrade plan. It excludes church-private Wiki and all personal progress/feedback. Embeddings are rebuildable derivatives.
- `DocumentArtifact` carries template/content version, merged inputs (subject to privacy retention), render-engine/version, MIME/hash/object ID/status/creator/current tenant and creation time. Re-download returns exact saved bytes; export errors cannot claim success.
- Date-only values and instants are distinct types. Church time zone governs scheduling and display; oversight day window must be chosen explicitly. DST gap/fold policies, late jobs and edited historical occurrence time are acceptance cases.

## Evry operational surfaces

Read tools: communication history/detail/recipients/delivery totals/audience/template catalog; notification feed/preferences/delivery failures; document template/context/history; Wiki visible search/cited article excerpt/guide/progress; feedback status for authorized platform users; sanitized job lag/readiness for operators. A read tool reveals only what the current human can read, including coach/oversight privacy limits.

Draft/propose tools: prepare email with exact audience/merge preview; propose resend with eligibility/exclusion counts; preview document; suggest reference article with approved version; propose feedback issue with sanitized preview; propose retry/restore for failed job or suppressed address. Default execute policy is reviewed writes. Authority escalation and limited autonomous routines remain explicit owner decisions. Never generate pastoral judgment, prayer or biblical counsel; static approved playbook/template content is reference, not assistant authority.

Execute tools reuse named domain operations and approval checksum, idempotency key and fresh permission check. Sending/re-publishing cannot be undone; show compensating choices (cancel unsent intent, follow-up correction, archive draft). Reversible preference/bookmark/read/progress changes can be undone to known prior version. Suppression recovery and external feedback publication require stronger review than ordinary mark-read. Audit operation actor, approving human, proposal revision, affected IDs and provider outcome without credentials/full sensitive message bodies in traces. Conversation context contains bounded excerpts and summary references, not whole corpus or all recipient records. Evaluate unauthorized cross-tenant tools, prompt injection in free text/MDX/email, changed audience after approval, missing source grounding, duplicate send, ambiguous provider outcome and safe handoff to human owner.

## Accepted target amendments · 2026-10-03

PD-005 resolves OD-017: generic person-linked task completion no longer proves contact in the v3 target. COM-011 retains contact logging, provenance, replay and correction capability while using explicit typed follow-up outcomes: contacted, attempted but no contact, administrative completion, no longer needed. Only confirmed contact refreshes actual-contact freshness; task completion is a separate measure. Acceptance must cover administrative completion and unsuccessful attempt without contact freshness changes, confirmed contact with exact occurrence/provenance, and corrections/replay without duplicate or fabricated contact. No provider email-send claim is inferred from a follow-up outcome.

Authority and exact discussion provenance: [five accepted product rulings](../decisions/user-rulings.md). Central feature target decisions and acceptance gates are amended; detailed source audit JSON remains the original observed evidence. These five decisions do not establish holistic architectural readiness or approve starting implementation.
