## 1. People, authority, privacy and ownership

### 1.1 Preserve distinct relationships rather than invent one universal role

**Recommendation — high confidence:** model account identity, plant seat, workspace Owner, designated primary planter, organization association, and platform administration as distinct fixed concepts. Coaching grants/accounts/modules are deferred by the latest ruling, not a current identity requirement. Evaluate the specific context of an operation. Do not union every authority the account happens to possess across unrelated contexts, and do not start with an arbitrary role/permission editor.

A sending-church/network relationship provides agreed oversight, not CRM ownership. An ordinary Owner grant is never consent to feed private care data to a model. The remaining owner decisions are meaningful:

1. Is the global original always separately accessible when an organization edition is selected?
2. Can a plant author its own edition/overrides, or only select a global/organization edition? Plant authoring is extra scope if not explicitly retained.

Retain the rubric's measured / attested / unknown distinction (`v2/product-docs/features/phase-engine/rubric-v1.md`, evidence discussion in §5b). Under it, distinguish an observed record, explicit human confirmation, and deterministic derivation. A model conclusion is an interpretation of cited evidence, not a new measured fact.

Missing, false, stale, retracted and not-applicable are different states. A stale attestation remains an attestation with an age; it does not become false or disappear into unknown. Only use not-applicable where the methodology explicitly permits it. Absence of a record is not evidence of failure unless the source contract establishes complete capture.

### 2.4 Attestation history and freshness

Current `plant_signals` stores signal key/value, attesting user and attested time with one current row per plant/key. `v2/src/lib/phase-engine/signals/attestation-service.ts:78` upserts that row. Current validators accept boolean/string/number values; a proposed closed seven-boolean catalog in v3 is a target tightening, not a description of all present storage constraints.

**Recommendation — high confidence:** a small closed typed definition catalog with append-only revisions of each relevant human confirmation. Retain definition version, subject scope, typed answer, actual confirmer and recorder, recorded time, effective/occurred time when meaningful, optional evidence references, and the prior revision/reason for correction, reaffirmation or retraction. Derive the current projection. Keep domain-specific records for launch, training, attendance, commitments and contact; do not move everything into an EAV “evidence” table or a universal event log.

Preserve actual freshness rules from `v2/src/lib/phase-engine/manual-signals.ts:87–171`: only `prayer_rhythm_established`, `prayer_in_gatherings` and `core_group_giving` have the 30-day reaffirmation rule. Values, funding base, prayer-leader and systems-tested signals do not all expire. Do not apply one blanket 30-day rule because it is easy to implement.

Retraction should visibly stop a current claim from being used while preserving what was previously asserted. False is a human answer, not missing evidence. A correction should identify what changed and why; a reaffirmation can record that a still-true assertion was checked again. The model never creates truth by inferring an attestation from prose or from private care.

Reaffirmation reminders are proposed UX, not a new pastoral alarm system: surface an aged confirmation when the user next works in the relevant context or in a calm digest. A neutral “assessment updated” notice may be useful for a materially new publication; do not notify on every recalculation or every warning severity. Organization Wiki editions cannot change these global executable rubric rules.

## 4. Notification foundation: preserve utility, simplify machinery

### 4.1 Actual capabilities to preserve

The v2 notification system has seven categories, in-app/email channels, per-recipient notifications, preferences, per-channel deliveries, digests and suppression records. These are not seven separate product requirements for a future generalized engine. Audit the actual producers and their user purpose.

| Existing capability / source | Preserve or clarify |
| --- | --- |
| Password reset/account emails via `v2/src/lib/email/client.ts` and auth callers | Preserve. Essential account email is not an optional task digest. Protect tokens, logs and non-enumerating responses. |
| Task due/overdue reminders, `src/lib/tasks/notifications.ts:80,83,104,142,262` | Actual producers are due/overdue. A category label is not proof of an existing assignment-notification producer. Preserve useful reminders; discuss calmer defaults separately. |
| Meeting reminders, `src/lib/meetings/notifications.ts:106,117,318` | Existing offsets include seven, three and one days. Audience differs for linked users, core group, creator and explicit guest email; do not collapse those semantics. Only future offsets are planned. |
| Meeting/guest outbound email | Preserve explicit guest/invitation email, with its real identity and audience rules, rather than assuming every recipient has an account or Inbox. |
| Explicit communications, `src/lib/communication/send.ts` | Preserve the distinct campaign/bulk communication purpose and consent rules while sharing transport reliability. V3 COM-005 and NTF-002 document that separation. |
| Plant digest, `src/lib/notifications/digest-content.ts:73,83` | Existing Sunday 16:00 plant-local scheduling and daily/weekly user preference need a deliberate parity/default decision; derive digest content from authorized current work. |
| Oversight digest, `src/lib/notifications/oversight-digest.ts:125,261` | Existing nonempty daily aggregation and scoped oversight views are actual functionality; do not grant CRM access through a digest. |
| Own relationship receipts / sharing changes, `src/lib/notifications/categories.ts` | Some messages intentionally describe a user's own former relationship or sharing change after that relationship ends. Preserve that narrow receipt history without treating it as ongoing plant authorization. |

Primary schemas: `v2/src/db/schema/notifications.ts:58,70,81,94,150,242,424,497,578`. Main audit: v3 NTF-001–NTF-014 in `docs/modules/communications-knowledge-ops.md`.

### 4.2 Recommended model

**Proposal — high confidence on architectural simplification, medium on UX defaults:**

1. **Domain history owns business truth.** Do not copy every domain event into a notification feed. A completed contact, attendance correction or launch change belongs to its domain, with a receipt/history appropriate to that action.
2. **One Inbox for useful attention.** A notice is a recipient-specific pointer to a canonical record or exact proposal revision. “Needs You” and “Updates” are useful views. Read/dismiss is not task completion, approval, cancellation or deletion of the underlying record. An approval notice cannot grant authority that the live proposal does not have.
3. **Future reminders use the shared durable-work mechanism.** In-app insertion does not need a simulated external-delivery claim/settlement pipeline. A bounded local notice can be inserted in the same SQL transaction as its domain change. Deferred fanout uses shared durable jobs. Do not build one queue per channel or a notification plugin framework.
4. **One shared Resend email intent/attempt/receipt path**, with purpose-specific authorization and consent for account, operational and bulk mail. Share reliability and provider reconciliation, not every policy. Retain a logical send key and frozen content/scope when relevant.
5. **Digest is a scheduled projection of authorized current work**, identified by recipient/scope/logical period. It should not be the residue of old Inbox rows. Dismissing a notice does not hide the underlying overdue task from the next digest. Missed periods should not cause a burst of stale catch-up emails.
6. **Keep preference storage straightforward.** V2's chosen/incidental preference intent and digest cadence interactions create unnecessary coupling (`preferences.ts:311–371,1082`). Prefer explicit overrides over defaults and separate cadence/scheduling from category enablement. Do not introduce a configurable rules language.
7. **Close notification rules over known types.** Dynamic consumer registration caused liveness behavior to depend on imports (`register-consumers.ts`; `dispatch.ts:260`). Prefer directly imported typed handlers/closed dispatch over runtime plugin registration with “unregistered means live.”

The parent research proposed a record-aware editable-context Evry panel, the same conversation at full width for cross-module work, exact before/after review, itemized receipts with partial failures, one Inbox, a read-only Home projection and progress inside the conversation. These are **unapproved UX proposals**, not requirements adopted by this review. They are compatible with the simpler model if they preserve exact review and atomic mandatory effects.

### 4.3 Real failure cases that justify a small reliability core

- **Stale but still live:** task liveness currently mainly checks existence/deletion/completion; meeting liveness mainly checks existence/cancelled/completed/future. A task date or meeting time/audience can change while the object still passes those checks. Cancellation of merely pending rows does not necessarily stop already claimed work. Proposed fix: a notification-relevant revision plus current recipient/purpose validation at send time. Do not use an unrelated edit timestamp to trigger endless replacement.
- **Stranded claims:** `v2/src/lib/notifications/dispatch.ts:305` has claimed/queued work without an adequate demonstrated recovery contract. Define leases and recovery; distinguish a known pre-send failure from an unknown provider outcome. Retry the former; reconcile the latter using stable provider idempotency/receipts, rather than blindly sending again.
- **In-app delivery machinery:** `dispatch.ts:923` claims/settles an in-app channel even though the notice row already represents the feed artifact. That indirection is a candidate for removal, not a product capability to preserve.
- **Webhook loss:** `v2/src/app/api/webhooks/resend/route.ts:250` catches processing failures and returns 200, so durable processing can be lost even when signature verification is sound. A small durable verified-event inbox/idempotent processor is justified; provider acceptance, delivery and user read are different states.
- **Transport idempotency:** `v2/src/lib/email/client.ts` correctly uses the provider's idempotency option rather than treating a generic mail header as idempotency. Preserve that contract and bounded retention assumptions when implementing the new transport.
- **Outage coupling:** a legitimate domain save should not fail solely because Resend is down. Commit its required durable email intent with the action, then handle delivery asynchronously. The user should see whether the record saved and whether delivery is pending/failed; no fabricated success receipt.

These are engineering defaults, not reasons to ask the user to design lease algorithms. The owner question is what the recipient should hear about and how much noise is acceptable.

Essential account email can be outside optional marketing/task preferences, but it must not bypass permanent address failure, abuse or security controls. Optional unsubscribe and an undeliverable address are different reasons to suppress. Avoid logging secret tokens or putting them into Evry/model context. Public account flows must not disclose whether an address has an account.

At read and send time, re-check current access to the target. A previously queued notice is not a permission snapshot granting future content access. Preserve immutable already-delivered history and the narrow own-relationship receipt exception; do not use those exceptions to leak plant records after revocation. Reviewed Evry email recipients/content cannot silently expand during execution.

### 4.4 New producers and defaults to discuss, not silently implement

| Proposed event | Recommendation and boundary |
| --- | --- |
| Assignment or handover | Potentially useful “Needs You” item, especially if responsibility changes. Verify it is new behavior where v2 has only due/overdue producers. Avoid notifying every bulk change independently. |
| Material meeting cancellation/time/location change | Potentially useful targeted update to the affected invited audience; not an email for every note/title edit. Re-evaluate who is still entitled to receive it. |
| Definitive failed or unknown delivery | One actionable incident per operation/batch, with retry/reconciliation state; not an alarm for every transient retry. |
| New Plant Intelligence publication | Neutral assessment-ready/updated item only when there is useful new information. No spiritual-health score alarm, prayer judgment or automatic severity escalation. |
| Evry run progress | Keep in the originating conversation/run receipt. Do not create a separate agent feed or fill the Inbox with every tool step. |
| Ordinary edits | Contextual confirmation and domain history are usually enough. No general “everything changed” notification stream. |
| Reminder defaults | Consider task email via digest and a one-day meeting reminder by default, while preserving configurable seven/three/one-day capability if parity requires it. These quieter defaults are a product recommendation, **not accepted**. |

For batching, a user may approve independent operations individually, but cannot approve attendance finalization while unchecking a mandatory domain-created follow-up. The review can explain the combined effect, group it as one operation, and show an honest receipt. “Partial success” is appropriate across independent operations, not inside a transaction whose invariant requires all effects.
