# Everyfield patterns

The coordinator owns these defaults, adopted on 2026-10-19. [Architecture decisions](decisions.md) records the owner rulings and their reasons. Requirements and acceptance cases define product outcomes. A deviation from these mechanisms needs a product reason in the PR.

## Performance

Every simple read or write finishes in under one second end to end on a production build. Reports and analytics may take longer and must say so in their PR. Count statements per HTTP request, the session lookup included. A simple write request sends at most six statements, independent of data size: the session lookup, then the write. A write on the one-statement path sends the change, its authority check and its audit row as one statement with no BEGIN or COMMIT. A write on the established path (C88) adds BEGIN, the write gate, its locked reads and COMMIT. A replay or a refused first attempt reruns the established way, and that run has its own budget. A page read sends a fixed number of statements for each page and each variant of it, however much data the page shows. Batch work with set-based statements rather than a statement inside a row loop.

## Request authentication and reads

One cached statement per request reads the session, its user and the viewer, keyed by the verified session cookie (RT-1). Better Auth's own session read runs only when that statement finds no live session (Better Auth then deletes the expired row and clears the cookie) or when the session is due for its expiry extension. Cookie cache stays off. The proxy checks cookie presence; domain code receives the verified viewer and does not resolve the session again. Prefer one short transaction per page render where practical, set-based queries and page numbers. Do not reread whole projections to answer a write.

The cached viewer names the actor. It does not prove access at the time of a later read. A read that returns tenant data puts the live check in its own statement as a predicate: the session is live, the seat in the selected plant or organization has not ended, the seat's role still permits the read and no lifecycle witness hides the account, owner or seat. The check adds no statement. When it fails, the read returns no tenant data. A stream or worker repeats the check in each statement it runs. The access.liveRead fragment in packages/domain/src/access/session.ts is that check as one condition (C13).

## Writes and concurrency

Include tenant and active-seat authority in the write statement. Zero changed rows means refused or not found. Normal writes need no separate authorize call or advisory lock. Use a revision column checked in the same update only where people can actually edit the same record concurrently. A pipeline move updates one row's sortable position key.

Known limit: writes for one account queue on the write gate, which locks the account row until COMMIT. This order is deliberate, not a defect. In F11, five parallel effect retries for one account waited up to 934 ms.

## Audit

Write one append-only audit row per write with tenant, actor, action, subject type and identity, occurred_at, permitted changed fields with their before/after values, and an optional request_key. Write it in the same statement as the change, using a CTE. Activity and history read this audit record instead of requiring a separate operation ledger, per-module result tables, event table and per-module history tables. The [audit contract](audit.md) still limits fields and excludes private care. Personal settings audit records the changed field names and the section revision, never their before/after values, because those values are personal.

## Safe retries

Use a request key only for actions a double submit or lost reply can repeat, such as forms and invitations. A unique tenant/request-key pair on that audit row lets a retry return the known result without writing again. Simple idempotent updates that set a value need no request key.

A native write's first attempt does not read its request key. A replay meets the stored key at its write and then reads the stored answer in one statement per key, with the request actor's live access and no transaction. A refusal whose first attempt ran on the write gate's locks, or sent no statement, is the answer; it reads the key once only when the command reached its key check. A refusal that rests on an unlocked read reads the key, then reruns the established way without reading it again. A failed statement reruns the established way.

## Side effects

Insert one job row with the change for mail and notifications. A worker sends it. Use a dependency graph only when a feature actually chains effects.

## Interface behavior

Update the screen optimistically with React optimistic state or local state. Confirm the result or roll back with a clear message. Update what changed after a successful action instead of calling router.refresh. Prefetch on intent rather than viewport visibility.

Effects, timers and wide component state are lint errors (D94). Instead of an effect, derive the value while rendering, do the work in the event handler that causes it, reset state with a key, subscribe to an outside source with React.useSyncExternalStore, or use a ref callback for logic about that DOM node. Instead of a timer that waits for something, act on the event, state change, promise or DOM node it waits for. A component or hook with more than four React.useState and React.useReducer calls first deletes state that should not exist (derived values, copied props, URL state, submit status, server data) and keeps the rest in a zustand store. The only exception path is a survivor entry in scripts/lint/survivors/<area>.json, with the function and its reason, which waits for Sebastian; existing code sits in scripts/lint/baseline/ until its area is cleaned.

The packages/ui primitives carry what a call site would otherwise patch around. Node observers in @everyfield/ui/foundations are ref-callback factories about their own node that clean up on detach: foundations.observeSize, foundations.observeIntersection, foundations.observeScroll(report, { root }), which follows the node's scroll column or, without one, the window, foundations.observeHeadings, and foundations.observeScrollProgress(report, { root }), both built on it; the progress observer reports the fraction of the node above the bottom edge of its scroll column (root) or of the viewport, after layout, on scroll and on resize, and leaves throttling to the caller. The window listeners these observers need are named survivor entries in scripts/lint/survivors/packages-ui-foundations.json, everyfield/no-global-listeners runs on their file and follows a host behind a conditional, logical or comma expression, a cast, an optional chain, and a variable declared or assigned from one (root ?? window), so a new one waits for Sebastian. The rule follows no data flow beyond that: a host passed as a function parameter, returned from a call or kept in an object property is not seen, and such a spelling is a review finding. foundations.useFocusRequest(request, pick, options) passes its focus options (such as FocusOptions.preventScroll) to the node it focuses, so a pick only chooses and never focuses by itself; foundations.useFocusOnChange(value, pick, options) focuses when value changes and never on mount or hydration, for a heading that takes focus when a step changes. A footer on a card's bottom edge that stays in view, such as a list's pager, is a controls.CardStickyFooter anywhere inside a Card that keeps its variant's padding: the card sets its padding, corner and fill as custom properties and the footer takes them, so no call site writes negative margins; a pager in it that disables the control just pressed moves focus to the other one (foundations.useFocusRequest), so focus never falls to the page. An avatar photo stays transparent over the initials until it loads; Avatar.onImageSettled reports loaded or failed once per image (also for a photo that settled before hydration), so a label names the photo only once it is known. Prose takes size md for an article, sm for a narrow panel and excerpt for a part of an article shown elsewhere (headings in the body face at text size, no outer margins), so no call site overrides its descendant styles with important classes. A Sheet that holds an inline form takes Sheet.onEscapeKeyDown and calls event.preventDefault there to close the form before the sheet. The shell's Ask Evry button takes AppShell.askEvryShortcut, rendered as data-shortcut so the page-event registry presses it, and AppShell.askEvryOpen, which states whether the panel is open (aria-expanded); pass a toggle as AppShell.onAskEvry.

## Client state

Remove state before storing it, in this order: submit status goes to React.useActionState or React.useTransition; fields are uncontrolled with a name and a default value; the packages/ui Select, Checkbox, radio group and Switch reset to their current default after a form action, as native fields do, and a controlled one keeps its value; server data comes from the server component, a promise it passes down, or the action's answer; URL state lives in the address; unrelated values split into components, with React.Activity when a hidden part keeps its state; a dialog opened and closed only by itself lets Radix own open. What is left over four state hooks goes in a zustand store: one per component instance, created in <Component>.store.ts by an exported create<Name>Store(init) with zustand/vanilla, held with store.useLocalStore and read with store.useStore, store.useShallow and store.storeContext (apps/web/src/components/store.ts). A store's init and port are captured once: pass values that change to actions, or remount with key. Actions live in the store and async actions read get(); props never flow into a store through an effect. Never call a store factory at module level and use no middleware; a tab-scoped module store needs its path in the lint allowlist (reserved for the meetings deletions store when that slice creates it). The everyfield/zustand-shape lint rule holds this.

Page-wide events have one owner each, installed once at module load; a component never registers a listener for its own lifetime, and a ref callback is legitimate only when its logic is about that DOM node. The address belongs to apps/web/src/components/location.ts: location.writeAddress(href, { replace, state }) writes it, location.usePath() and location.useAddress() read it in the same event as the write or the Back press, location.addAddressRule(rule) registers at module scope a function of the next and previous address that rewrites an address no screen can show (it runs on every write and every Back or Forward, including a Back from another page that mounts the screen from the router cache, where no server redirect and no component listener runs), location.onTraversal(listener) is for work an event started, and location.onNavigation(listener), also started from an event and released when its work ends, hears every navigation Next.js's router starts (a link, router.push or router.replace, Back or Forward) with its target address, before the page changes, through the router transition hook Next.js calls in apps/web/src/instrumentation-client.ts; a link, push or replace whose target is the address in the bar when it starts (a fragment link) is not reported, every Back and Forward is, one between two entries of the same address too, and nothing reports when the new page has finished showing. The address fragment has one paved path too: a client component reads it with location.useAddressHash() ("" on the server; it follows in-page links, store writes, Back and Forward), and event code reads it with location.addressHash() and writes it with location.writeHash(hash), which makes the same single history entry a fragment link makes. The location store reads nothing from the address while its module loads, so it may load before or after the one-time link script. A one-time link value, one an emailed link carries in its query or fragment and that must not stay in the address, is registered by page in apps/web/src/components/one-time-link.ts: it leaves the address before the page hydrates, in one replace that keeps the entry's state and history length, and is handed to the page that asked for it; the location store does the same when a same-document navigation brings one in. location.useOneTimeLinkValue(name) only reads it (undefined until hydrated), and location.forgetOneTimeLinkValue(name), called in the event that ends its use, drops it. A screen that receives a query value from its server page keeps its first one in React state so a router refresh shows the same form. Shortcuts and the unsaved-work warning belong to apps/web/src/components/save/leave.ts: the form that performs an action carries leave.shortcutMark(combos) and its shortcut submits it (the submit handler decides what a press during a running action means), a marked control is clicked only when it is enabled and not busy (otherwise the key passes on), and a form renders data-unsaved while it holds unsaved work. A character shortcut such as / matches whether or not the keyboard layout needs Shift to type it, and a combo that names Shift needs it; leave.shortcutMark(combos, { claim: true }) keeps the browser's own action for the key from running while the marked control is disabled. A key without modifiers is ignored while focus is in a field, unless its leave.shortcutMark opts in to fields, as an open menu's Escape does. A form that must ask before the person leaves renders leave.leaveHoldMark(unsaved) and calls leave.armLeaveHold() in every event that makes its work unsaved (it arms at once, before the form marks itself): the registry then holds an in-app link click, leave.leavePage and Back (through a guard entry at the same address) and publishes the question through leave.useLeaveRequest(), whose leave and stay answer it; Leave follows the same link, goes back or runs the held action, and the browser does not ask again before a sign-out unload. An action the person already chose to leave by, such as discarding edits to reload, calls leave.leaveNow(go), which runs it without asking and without the browser's own question. A question that is not answered goes with its page, and every later editor of the tab asks again. An element whose last write must go out when the page is hidden renders leave.leaveBeaconMark({ url, body }), and the registry posts each marked body once with keepalive on pagehide. An address rule is registered by name, so registering it again replaces it. No feature calls history.pushState or history.replaceState, listens to popstate, reads or writes location.hash outside those, uses the Navigation API, or writes an in-app address that carries a one-time link value (everyfield/no-raw-history, which cannot see an address built with a URL object), and no feature adds window or document listeners, media-query listeners or observers of the whole document, or creates an observer at module load (everyfield/no-global-listeners, in apps/web/src and packages/ui/src); a listener that truly must follow a component's lifetime is a survivor effect.

A client read is one read.createRead(load, { failed, fresh }) cache (apps/web/src/components/read.tsx), and nothing a reader runs while rendering starts a load. A read starts in an event that asks for it (read.prefetch or read.get in the click, intent or submit handler), from the server (read.seed with the value or promise the server component passes), or, when neither happened, on the cache's first subscription to that key, which is how an external store connects to its source. A loader only loads its key (everyfield/read-loader): any other effect in it would run once per key on first subscription, a mount hook with no cleanup. A prefetched or seeded entry is current only within the read's fresh window, like any other. read.useRead(cache, ...args) returns a snapshot of the cache for that key (status, value, reloading); every reader of a key follows refresh, retry, patch and forget. read.Await shows today's loading markup until a value exists, remounts its children on a new key and on retry, and keeps them through a reload; a view that must keep one element mounted while it loads reads value directly. Args are keyed with JSON.stringify, so they are strings, numbers, booleans or plain data, never undefined, dates or functions. The read cache holds nothing on the server: seed, a load and a patch there store nothing, so a server render never leaves a value in the module. A read keeps at most its limit of entries (200 by default), dropping the oldest one no reader shows. A patch while the entry loads is applied once to the value that arrives, so a patch must be idempotent (keyed by id): that value may already hold the write. The patch a reader's read.useRead returns re-renders every reader of the key through its own update in the caller's transition, instead of an immediate notification; a listener connected without read.useRead is notified at once. In the teams adoption, a row patched in from inside an async action showed next to its still pending React.useOptimistic row for one commit, so an optimistic add still drops its pending row once the saved row is there. read.useReadWith(cache, args, options) is read.useRead with reader options: options.newerThan, the time the server read the page, reloads an older entry once on this reader's first subscription while every reader keeps its value, comparing it with the server time the read's served-at option takes from each value (a read without it counts every settled entry as older), and options.showPrevious keeps the last value the reader showed on screen while the next key loads, whether or not the option was on when that value arrived; a null read drops it, so the first key after a cleared search shows nothing kept. read.useLocalRead(load, options, ...args) gives one component instance a cache of its own, for a read two instances must not share. Waiting for a typing pause uses foundations.createDebouncer from @everyfield/ui/foundations, destructured where it is held so that debouncer.cancelOnDetach goes straight on the input's ref.

## Code layout

Code one feature owns lives in apps/web/src/features/<feature>/: its screens, server actions, server reads, mounts and jobs. app/ holds only route files and Next metadata files; each imports one feature, and a route file only re-exports it or sets route config. Another feature may import a feature's file only when scripts/lint/boundaries/apps-web-features-<feature>.json lists it as public with its reason; code several features share moves down into apps/web/src/components or a package. apps/web/src/server holds platform code only and imports no feature, packages never import the app, an import names a subpath its package exports, and packages depend only on the packages below them. Inside packages/domain, packages/contracts and the Evry adapters, a module imports another module's index.ts, a kernel module or a file on that package's public list. features/shell, the cron jobs route, the scheduler and the Evry runtime wiring compose many features. Lint enforces all of this (D95).

## Verification

Test the exact behavior a user sees under test-standard. One statement check covers every budget in tests/integration/writes/limits.json: real HTTP requests on the production build, the native write boundaries and every write the behavior suites run. It runs in GitHub CI (three parts and their union) and in bin/dev check for any diff that touches backend or database code, so a seat sees it before evf pushes. It fails when a run goes over its budget, when a write has no budget, when a budget is never measured, when a write above six statements has no reason, when a page sends more statements as its data grows, and on N+1: one statement shape (its text with values stripped) sent more than twice in one first attempt, even inside the budget, unless the entry's repeats names why the repeat is fixed rather than per row. Slack never fails. A run that measured every suite tightens the file instead: each first-run budget comes down to the most statements measured, a reason or repeats no longer needed is removed and a retry run with no retry budget gets one at its count. bin/dev check writes the tightened file into the worktree to commit with the change; the CI union job prints it in its summary and uploads it, and no job pushes a commit. A retry budget is an upper bound, because its count depends on which racing write lands first. Reviews judge code quality against these patterns and the principles, and verify the performance budget, optimistic behavior and unnecessary requests.
