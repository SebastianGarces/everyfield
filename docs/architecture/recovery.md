# Deletion and recoverable state

Product cancellation and recoverability are distinct. Personal-account deletion is requested by the authenticated account; plant workspace deletion by its current Owner alone. Owner/Admin ordinary administration does not give Admin workspace deletion. Existing manual exception for an Owner leaving a continuing workspace remains identity-owner work, not a transfer/rejoin engine. Provider selection does not authorize setup, paid spend or a restore now.

## Deletion lifecycle

Use lifecycle fields on `app_account` and `plant` aggregates, domain-owned history/audit/command receipt, minimal `deletion_witness` and recovery manifests. No deletion-request workflow platform or blanket cascade. Each request has immutable request ID, revision, requestedAt, cancelUntil=requestedAt+30 days, initiating actor and exact typed subject. States are active→pending_deletion→purging→purged; cancel is pending_deletion→active strictly before cancelUntil. One subject lock/CAS and DB clock fence request/cancel/purge claim; stale cancellation cannot affect a later request.

At request commit, revoke affected normal sessions/authority, hide affected content and stop normal reads/writes/streams/model/context/history/file issuance/exports/org directory and health contributions/new provider handoffs. Data is held privately solely for cancellation. Account request does not hide unrelated independent plant/organization-owned records from their valid readers; workspace request hides all its owned data/contributions for every affected account/organization. Active-subject checks apply in native/Evry/jobs/DTO/query/count/group/cache/file paths, not navigation alone. Private care stays author-private and absent from every other-purpose path throughout hold, purge and restore.

A narrow native cancellation-only authentication purpose permits original-account identity proof or requesting current workspace Owner identity/current authority, request status and cancel action; no ordinary sessions/private bodies/other subject. It uses established fresh native proof, current request and purpose token, not an old revoked session. At exact deadline cancellation fails even if purge is late. Successful cancellation restores only independently still-valid grants/access, creates a fresh normal sign-in opportunity and never revives independently revoked affiliation/role, another pending subject, old session or canceled provider mail. Account deletion cancellation cannot override a workspace deletion.

Only an actual account or plant is a requestable subject; the independent organization root has no public workspace-deletion operation. At/after deadline, internal `maintenance.purgeEligibleSubject` admits only the registered deletion job with exact actual account/plant, request ID/revision/deadline and current claim generation, then claims pending→purging. Bounded `deletion.purge` works from a typed owned-reference manifest, records completed chunks and keeps everything denied after failure. Eligible database data, hosted artifacts/caches/derivatives and private object content are purged coherently. `livePurgedAt` is set only after every eligible live DB/file reference is removed or scrubbed according to its ownership contract; an object delete timeout is not completion. Minimal current witness records subject/request/revision, livePurgedAt, copyExpiresAt≤livePurgedAt+7 days and cleanup outcome without deleted sensitive payloads. No post-deadline normal user restore/cancellation right.

| Account-owned native documents/revisions/imports/avatar/personal reading/bookmarks/feedback original/private care | Privately held for cancellation, then owned live content purged; private-care existence/calendar/nudge metadata never broad audit. |

Schema/reference owner assigns purge/detach/minimal-attribution to every FK/resource. Neither universal CASCADE nor universal permanent-audit exemption is valid. Audit follows legitimate owner lifecycle and explicit minimal scrub; no extra broad audit browser/export or unapproved retention exception. Recopying/restoring cannot reset subject expiry. At restore, current witnesses override historical images before access, including their pending/expired state.

## Selected recovery configuration

Configure and verify Neon seven-day point-in-time history plus daily snapshots; a paid default one day is insufficient. Daily snapshots expire at seven days and the cleanup sweep also covers manually retained/latest-preserved snapshots, restored branches and old test endpoints. Configure Tigris seven-day deleted-object recovery and explicitly clean soft-deleted buckets, earlier versions/snapshot markers and stale objects. These retain recoverable copies, not normal online data rights. Provider physical deletion may be asynchronous; logical inaccessibility and attempted/confirmed provider cleanup remain separate and observable. Never promise universal physical erasure on calendar day 37.

Selected daily backup destination is a **separate private Tigris bucket**, with dedicated bucket-scoped credentials and encrypted dated copies. It is not a prefix in the production bucket, not a second provider and not independently hosted disaster recovery. Same Tigris provider/account failure risk is accepted and disclosed. No object-lock guarantee, independently hosted launch gate or multi-provider platform is introduced.

## Restricted backup context

Use an operator-only maintenance CLI built from the same approved application source artifact on a positively identified restricted operator workspace or approved existing runner. Internal `maintenance.restoreWithCurrentManifest` requires the restricted exact project/environment operator capability, actual manifest/key-version and current deletion-witness scope; it is not an app/model/customer/native general recovery grant. It is scheduled maintenance, not a second deployed product worker. Actual host identity, daily schedule, availability, artifact revision, account/key delivery and access are future configuration inputs and proof gates; this document does not claim an existing host is available.

That process alone receives dedicated DB consistent-snapshot/read-only access, production-object read/recovery capability, private backup-bucket scoped write/read/expiry access and recovery encryption-key material. Ordinary Next runtime, ordinary Vercel environment/build/preview, application object credentials, Evry/model/log/telemetry and customer requests receive none of the backup-bucket credential/decryption key. A separate env variable in a shared app process is not isolation. Actual negative provider-access and build/runtime secret-delivery tests must prove exclusion. Keys are escrowed under actual authorized backup-operator recovery control; record key version and recoverability without logging keys. Backup copies preserve purpose-encrypted private content without exposing it as operator/model-readable narrative.

The CLI performs `backup.daily`, witness sync, expiry and isolated restore using the same manifest/job/receipt conventions, with its own scoped maintenance authority. It polls/syncs current minimal deletion/access witnesses at least every five minutes while normal service is running and performs a verified daily full DB-plus-byte candidate. This is low-volume maintenance, not an additional product job platform. A missed schedule records lag and blocks any unproven fallback claim. Actual scheduler configuration requires setup authorization and evidence. No routine app endpoint can pass an arbitrary backup key/destination into this process.

## Coherent copy and restore protocol

`recovery_manifest` is immutable candidate ID/artifact/source version and consistent DB snapshot instant/LSN, DB checksum/size, exact referenced ready object IDs/version keys/MIME/length/checksums, encryption/key version, current witness checkpoint, copy creation time, artifact expiresAt, each embedded subject's non-resetting expiry origin and verification status. Snapshot/artifact checksum and authenticated encryption cover the manifest itself. Upload/document pending/ready/failed state is retained. Inventory pages are deterministic; no unresolved/truncated page may be called complete.

For ordinary recovery choose one DB point no more than one hour behind the last committed recoverable work. Immutable production object keys/metadata plus native seven-day object recovery must provide every referenced ready byte at that DB point, including replaced/deleted objects. A daily byte backup alone cannot prove one-hour RPO. Object readiness is committed only after actual upload; orphan/pending objects do not fake ready files. Snapshot record pins exact immutable references; concurrent writes after snapshot do not contaminate the byte inventory. Missing bytes/checksum mismatch marks the copy incomplete; it is never promoted as the latest successful daily backup.

Restore is operator-authorized into an isolated DB/bucket with normal user access/jobs/mail/issue publishers disabled. Recover/decrypt the manifest, verify source/schema and all DB/object checksums, restore exact point and matching bytes, and obtain **current** authoritative deletion/access witnesses outside the stale image. Use the surviving live witness state for ordinary mistake recovery and the separately synchronized current journal for fallback. A stale checkpoint or uncertainty about intervening deletion/access decisions fails closed; daily fallback has no authority to expose potentially expired subjects. Witnesses contain no body and outlive the copy only to prevent prohibited resurrection.

Apply pending/purged/expired denial and cleanup before reopening. Reconcile accepted/scheduled/unknown email and issue receipts against actual external facts/current journal; never replay provider sends/issues merely because restored local row says pending. Invalidate old sessions/tokens/URLs/context as required, re-evaluate current entitlements and prove no expired private bodies/caches/org projections. Restore test checks that canceled scheduled sends remain canceled. Only then operator records current coherent recovery receipt and permits fresh authenticated service. Cleanup restored branches/temporary objects/unencrypted workspace copies/older snapshots explicitly; truthful completion includes observed inaccessible/confirmed cleanup states.

## Recovery targets and later evidence

Ordinary recoverable application/operator mistakes with live provider access have internal RPO≤1 hour/RTO≤4 hours, measured from incident declaration to verified coherent DB+byte service recovery. This is a goal requiring actual demonstration, not customer SLA. A sufficiently fresh successful **surviving accessible** daily encrypted copy may provide ≤24-hour data loss fallback; a scheduled-but-failed copy does not. Shared provider/account loss can affect primary and backup, so there is no guaranteed disaster availability/RTO/SLA.

Before real customer data, actual cost approval and configuration verify history/snapshot/object retention, daily encrypted candidate freshness, backup credentials absent from ordinary app/build/preview, recoverable key access, coherent restored files, current deletion barrier and non-replay of external effects. WP-003/004/037/050 own proof; WP-056/057/058 enforce release. Named DEL58-001–009, REC59-001–006, BKT60-001–004 and RECOVERY engineering fixtures remain future. Capture actual incident/snapshot/recovery instants, lost-work bound, checksum manifest, scoped authorization checks, provider expiry/cleanup and operator evidence. A failed drill leaves the before-real-data gate open; repeat after material recovery change rather than claiming evidence from file presence.
