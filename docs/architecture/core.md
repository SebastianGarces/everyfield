# Core architecture

EveryField is one modular Next.js application on the selected Vercel deployment, with application-owned Better Auth, PostgreSQL on Neon, private Tigris objects, Resend mail and the selected model adapters. Node 24 is the runtime target; dependency pins and their actual compatibility proof belong to the dependency contract. Domain functions own behavior; Server Components, Actions, Route Handlers and Evry adapt those same functions. There is no separate backend, queue provider, workflow platform, universal entity graph or customer migration.

## Boundaries and ownership

`packages/contracts` owns typed request/result/error/date/scope contracts. `packages/db` owns one schema release, the pool and short transaction primitive. `packages/domain/src/<domain>` owns current rules and safe projections. `packages/integrations` owns provider boundaries. Evry owns conversation, proposal/review and composition; each domain adapter owns its manifest and calls the same domain operation. The package/DAG catalog specifies the disjoint implementation paths and integration owner. These folder boundaries need not become separately published packages.

`CommandContext` is constructed on the server from a current authenticated principal, one exact acting plant/organization/account scope, purpose, request ID and origin. Organization context includes kind and ID. A caller may provide subject IDs and expected revisions; it cannot provide trusted role, actor or grants. Account identity, CRM Person, ministry role, account seat, discovery relationship and affiliation are distinct. One account has at most one active tenancy seat. Platform grants are separate bounded permissions and never a private-data wildcard.

Authenticated-self account context also serves an explicit Discovery profile without a tenancy seat. Assistant account rows bind `account_id=owner_account_id` and have no plant/organization IDs. Only currently authorized own preplant documents, approved global Wiki and Discovery operations enter that context; it creates no tenant grant and exposes no credential, secret or private-care model/tool surfaces. Plant and typed organization assistant contexts require fresh exact grants while their conversation/history remains private to the original account owner.

Plant roots and typed organization roots remain separate. An organization has immutable `sending_church` or `sending_network` kind; every organization child/bridge uses `(organization_id,organization_kind)` against `(id,kind)`. Plant children use `(parent_id,plant_id)` against `(id,plant_id)`. Bilateral affiliations have exact pair and recognition episode; they do not transfer ownership or inherit a parent network grant. Global approved references and private global identity are explicit exceptions, with different access policies. [The physical catalog](../schema/target.json) specifies every field, key, constraint, immutable owner and deletion reference.

## One short transaction protocol

`withDomainTransaction(context, command)` supplies one interactive PostgreSQL connection. The orchestrator locks roots and required subjects in a stable order, rechecks live session/grant/scope/lifecycle, checks request digest and expected revisions, and then commits the owned changes. Collaborating domain functions receive that UoW; they do not call HTTP or a public Server Action inside it.

For a meaningful domain mutation the same transaction writes the current aggregate, required domain history, all synchronous material-evidence revisions, `command_receipt`, typed `audit_event`, and required local inbox or durable effect/job/mail intent. Audit or required-intent failure rolls the mutation back. Better Auth owns its own credential/session/verification mutations: significant credential operations have durable security intent and verified outcome reconciliation, never an assumed shared domain UoW. Ordinary session renewal is neither a PI writer nor a canonical business event. Private-care changes use author-private history instead of central audit and do not touch PI material revisions. No-op or idempotent replay returns the original receipt; reusing a key with different normalized input is `idempotency_conflict`. Unique domain identities still arbitrate recurrence, obligation, invitation and assignment races separately from command retries.

| Operation | Atomic database responsibility | Work outside the transaction |
|---|---|---|
| Domain registration acceptance | Valid token claim, seat/relationship, required Person/link, account activation, receipt/audit/mail intent | Better Auth credential creation is a prior resumable stage; security mail dispatch follows commit |
| Actual plant creation | Lock account/seat; new plant, Owner seat, Person link, one creation-origin Phase 1 transition, selected document copies, receipt/audit | Notifications and expensive rendering |
| Human evidence/correction/merge | Owned record, permitted stage change, typed history and registered references, source revision, receipt/audit | Irreversible provider evidence is preserved; inverse refuses conflicting later changes |
| Meeting attendance finalization | Participation revision/marker, stable obligation kernel, managed follow-up/evaluation tasks, domain event, receipt/audit/intents | Delivery only; WP-024 kernel must precede WP-022 |
| Task completion and recurrence | Dependency guard, status history, exactly one logical successor with fresh one-level child task rows, receipt/audit/intents | Reminder dispatch |
| Training roster change | Reviewed deduplicated exact Person/program/requirement-version episodes and history, source revision, receipt/audit | No invisible live-roster recomputation |
| Assessment publication | Validated output and pointers after source/reference/grant/contributor/job-generation CAS | Immutable consistent snapshot preparation and model inference |
| Launch submission/publication | One canonical occurrence/count aggregate, version history, submitted evidence or separately reviewed sharing summary, source revisions | No automatic phase transition or new Launch Meeting |
| Reviewed Evry mutation | Exact approval/digest/actor/effect/version guard, same native transaction and effect receipts | Provider/model calls and reconnect streams |
| Deletion request/purge | Aggregate request/deadline/revision fence, immediate access denial, cancellation of intents, owned cleanup including source-containing organization NI run/result/history copies and current witness | Provider cancel/reconciliation, object cleanup and original source recovery-copy expiry |

Credentials and domain acceptance follow exactly [the staged auth protocol](auth.md); this document makes no credential-plus-domain atomicity claim. The pool must support read/lock/write transactions. Compatibility and separate-connection failure/race tests are future proof, not evidence already achieved.

## Durable execution

Ordinary asynchronous work uses the same application artifact and an authenticated bounded Next Route Handler. PostgreSQL `job` rows are durable authority. A tick claims eligible rows with `FOR UPDATE SKIP LOCKED`, advances claim generation and releases locks before model/provider work. Completion/checkpoint/publication compares the current generation and lease; a resumed stale invocation cannot publish. Claims have a finite lease, bounded attempts/backoff, exact job kind and subject scope, per-kind budgets, per-tenant fairness and a truthful failed/reconcile terminal path. The operations contract owns the concrete per-kind limits, acceptable lag and operator recovery steps.

`after` may wake already persisted work; process lifetime and streaming cannot be the durability guarantee. Direct local inbox writes need no dispatch state machine. Communications, notifications and security mail share `email_intent`/`email_attempt`; native scheduled mail uses the provider schedule rather than a second scheduler. Unknown provider acceptance stays unknown until reconciliation; changing provider keys is not recovery.

Encrypted daily backup, restore and recovery-copy expiry use a restricted operator-only CLI from the same artifact. Its encryption and backup-bucket credentials are absent from ordinary Next environments, builds and previews. A controlled execution context and measured schedule must be configured and proved before customer data; no existing host or additional provider/deployed worker is claimed. The CLI is an explicit operational boundary, not a public Next route or tenant capability.

## Dates, references and safe projections

`LocalDate`, `LocalTime`, confirmed IANA zone and `Instant` are different values. A date-only deadline is due through its plant-local day; a timed deadline uses its resolved instant. Explicit gap/fold appointments require human choice and save resolution provenance. The follow-up due date is meeting local date plus two calendar days; the performance metric uses exactly 48 elapsed hours from the immutable actual origin instant. Completion alone never proves contact. Fixed appointment instants and historical snapshots do not move when a zone changes; future recurrence/reminder changes are previewed, revisioned and replanned with stable logical slot identities.

Global article/source/version IDs and immutable release manifests own reference lineage. Activation commits only complete validated eligible derivatives; rollback appends a new activation. Organization Wiki bodies require current entitlement on every body, history, citation, cache and file access. Plant Wiki precedence is the currently eligible first explicit edit/hide in ordered sending-church sources, then networks, then global; preferred is derived from the order. Local writing uses owned Documents. One eligible actual reader must complete all six canonical Discovery articles at strictly more than 80%; disjoint readers cannot pool, updates do not erase earned credit, and Phase 1 creation is independent.

No shared persistent private DTO cache is enabled initially. Every get/list/count/search/export/RSC/stream/download/context builder applies current authority and named field projections. Raw rows and protected contributor manifests never become transport DTOs. Freshness and model-publication details are in the assessment contract; upload/mail/recovery execution details are in the operations contract.

## Proof and limits

The current specification chooses the complete design. Physical constraints, real auth integration, concurrency, rendering, model evaluations, provider reconciliation and coherent restore/purge remain `future-not-run`. Named cases are in the consolidated acceptance catalog and this track's handoff. Actual paid plan/monthly spend, credential setup, repository identity and promised merged development workflow are external inputs. Free development allowances do not prove production invocation or recovery capacity. No application, provider account, database, customer record, spend, PR or deployment was changed by this consolidation.
