# Platform audit

`audit_event` is a small platform-owned append-only table under WP-002/004. Domain packages produce their own typed actions; WP-050 owns scoped investigation and policy-controlled cleanup; Evry producers preserve approval/execution lineage under WP-051/053. Audit is committed attribution and security evidence, while domain history owns content/revisions and operational ledgers own delivery evidence. It is not a universal event bus, row-snapshot store or source of current business state.

## Envelope and append path

The [physical catalog](../schema/target.json) enumerates ID/time/action/version, exact typed owner and affected resource, before/after revisions, actual human/service actor, origin, initiator/reviewer/approval/plan/execution linkage, request/event keys, outcome/reason and metadata. `resource_id` is a stable historical identity: `appendAudit(uow,context,event)` validates the live subject's exact scope at append, then allows a minimal receipt after subject removal. It never authorizes a later read.

`appendAudit` accepts only the closed versioned action schemas below, constructs actor/scope from trusted context, and verifies the resource and optional lineage match the transaction. It serializes JSON as UTF-8 and rejects metadata above 2048 bytes; SQL adds `octet_length(convert_to(metadata::text,'UTF-8'))<=2048`. Metadata is an object with only schema-allowlisted fields. No entire-row serialization, arbitrary safe-looking diff or general JSON search index is allowed.

Action metadata variants are separate schemas even within a family; sensitive field names/counts are allowed only when that action's projection permits them. Raw interview/4 Cs values remain plant human-record permissions; photos, addresses, prompts, mail bodies, attachments, credentials, headers, signing keys, token values and signed object URLs are excluded. An action/resource/type cannot be created dynamically from a URL or user/feedback instruction.

## Transactional truth and external outcomes

Successful meaningful domain mutation, domain history, audit, command receipt and required effect intent commit in one short transaction. Audit failure rolls back the change. Idempotent replay returns its original receipt/event IDs and adds no fictitious second change. Bulk mutations use per-resource events or a bounded same-scope manifest identity; cross-tenant records cannot hide inside a tenant-readable JSON payload.

Better Auth credential/session/verification statements are a distinct adapter-owned boundary. Significant credential mutation begins with an atomic domain security-intent/audit and an account authority fence, then calls the adapter outside the domain transaction; outcome is appended only after verified result or atomic adapter marker reconciliation. Credential success can therefore precede its recorded app outcome, and the fence remains until reconciliation. Initial credential identity with a missing app-account row is unprivileged; authenticated resume observes it, creates the unique pending row and records a truthful reconciled outcome. Ordinary session renewal and bounded failed-auth telemetry are not canonical business audit. This does not weaken atomic token/grant/Person domain acceptance.

Denied/rolled-back commands cannot have a successful event from that transaction. Significant denial/failure evidence can append in a separate transaction after rollback with truthful outcome and safe code; a telemetry failure does not make an ordinary harmless read fail. Provider work happens after intent commit and outside locks, then acceptance/delivery/refusal/unknown/reconciliation evidence links the existing effect. Duplicate callbacks are deduped; out-of-order events cannot rewind monotonic delivery state.

## Private-care exclusion and access

Private check-ins have author-private native revision history and **no central audit entry**, including titles, row IDs, timestamps, weekly-calendar/period/answer existence, nudge counts and access-open events. They also have no model/Evry/export/org/email/PI/log/trace/evaluation path. A broad account-purge receipt can say the authorized private purge completed; it must not name/count care subjects. General `record_correction` is not their history store.

Audit access is internal, explicitly purpose- and scope-bound. Tenant Owner/Admin and organization affiliation do not create a broad audit browser/export. Ordinary platform administration does not grant private narratives. A privileged investigation/export must authenticate the current bounded operator grant, apply exact row/field projections, use cursor-bounded pages, and record its own access. Default indexes are per-owner newest-first, per-resource history, scoped semantic event key and execution/correlation lookup; no blanket JSON GIN index, hash-chain, event-sourcing or launch partition platform.

## Actor deletion and retention

Live actor/initiator/reviewer account links are nullable. Personal purge replaces legitimate shared attribution with an opaque deleted-account token local to the owning scope and clears unnecessary live identity linkage. It never copies email/name or retains a universal cross-tenant actor map. The token is pseudonymous rather than guaranteed anonymous. Human versus service execution remains truthful; unattended maintenance has typed service identity and purpose, never an invented human approver.

Account-owned audit details purge with private account data; plant-owned audit purges with the plant. A counterpart keeps only its minimum legitimate relationship-ending receipt, not a plant snapshot or private subject list. There is no general audit-retention exemption or approved separate audit period. Ordinary writers cannot UPDATE/DELETE audit; a distinct privileged policy cleanup may scrub/purge for deletion and correction is an appended event. Database-owner power means this is not WORM or tamper-proof storage. Restored snapshots must apply the current deletion witness before access; seven-day copy eligibility never resets.
