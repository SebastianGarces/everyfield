The fresh build has no customer migration constraint. It can discard accidental implementation complexity while preserving the product's SME foundations, privacy, history and operational needs. Evidence paths below refer to the audited v2 baselines; the module specs explain complete behavior.

## October 8 grounded email reliability lesson

The verified incident lesson distinguish the reported repeated failed webhook deliveries/provider disablement from the verified v2 route that logs processing/suppression errors and returns200. The cause is unconfirmed; a bounded log window without matching evidence and the presence of a signing secret cannot establish cause or correct configuration. V3 needs actual verification fixtures, durable receipt before acknowledgement, restart/partial-consumer retry, idempotent replay and operator-disabled/unknown endpoint visibility. Retain bounded sanitized correlation evidence. No immediate repair or provider action; the user allows it to wait for v3.

The consolidation caught misleading checklist helper names: their verified native actions use real one-level child Tasks with assignment/history. A separate proposed checkbox table and three public operations were redundant. The target now uses the child Task/status-history model; legacy checklist names are typed aliases. This simplifies persistence without losing independent child assignment, completion history or fresh recurrence reset.
