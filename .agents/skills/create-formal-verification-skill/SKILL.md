# Create a formal verification skill

Formal checks cost a model, a map and a conformance test to keep current, so Everyfield spends them only where a
bug costs the most: **permissions and billing** (ruling D93). Do not model another subsystem; ask the owner first.

- Permissions has its skill: `.agents/skills/formal-permissions/`. Read it as the worked example of every step below.
- **Billing is next**, once billing code exists. On 2026-11-15 there was none: no billing package or code in
  `packages/`, `apps/` or `tools/`, no billing work package in `docs/plan/dag.json`, and REQ-IDN-026 excludes it.
  Search again before you start (`git grep -il billing -- packages apps tools`).

Every subsystem uses TLA+ with TLC, the pinned `tla2tools.jar` and the one command `bin/dev formal`. No Lean and no
second tool.

## Layout

| Path | What |
|---|---|
| `formal/<subsystem>/<Name>.tla` | The model: state, actions, rule operators, properties and the outcome table |
| `formal/<subsystem>/MC<Name>.tla`, `MC<Name>.cfg` | TLC's model: constants, `VIEW`, `INVARIANTS`, `PROPERTIES` (exactly one `MC*.cfg`) |
| `formal/<subsystem>/outcomes.json` | Generated by `bin/dev formal --write`; never edit by hand |
| `.agents/skills/formal-<subsystem>/SKILL.md` | The subsystem skill (this skill's output) |
| `.agents/skills/formal-<subsystem>/map.json` | Each model action, rule and property, its code and its ids |
| `tests/integration/<area>/formal-<subsystem>.test.mts` | The conformance test |

`bin/dev formal` (`tools/formal/formal.ts`) finds every `formal/*/` model and every `.agents/skills/formal-*/map.json`
by itself, so a new subsystem needs no change to the command.

## Steps

1. **Pick the properties.** Read the subsystem's requirement JSON in `docs/catalog/requirements/*.json` and the
   rulings in `docs/architecture/decisions.md`. Write each property as one sentence a bug would break, with the
   requirement or decision id it comes from. Prefer the properties whose failure leaks data, grants authority or
   moves money. List them, lettered, in the subsystem skill.
2. **Write the model.** State is what the code persists (rows, their state columns, sessions). One action per
   operation the code exposes, guarded as the code checks it at commit time. Put each permission or price rule in a
   named operator (`MayChangeSeat`, `LiveCheck`) that both the actions and the outcome table use, so neither keeps a
   second copy. Model a request that reads first and writes later as two steps (resolve, run) with any steps between.
   - Invariants for state facts; action properties `[][P]_vars` for "no step does X". Record the step just taken in
     a `last` variable that no action reads, and leave it out of the `VIEW` so it adds no states.
   - Bound everything (accounts, slots, revisions) so TLC finishes in under a minute on two cores. Shrink the
     constants or fix the initial state before you weaken a property.
   - End the module with `ASSUME PrintT(<<"outcomes", Rows>>)`: a set of string tuples, one per case the
     conformance test runs, whose last element is `"allow"` or `"refuse"` from the rule operators.
3. **Write the TLC config** `MC<Name>.cfg`: model values, `Name <- MCName` substitutions from `MC<Name>.tla`,
   `SPECIFICATION Spec`, `VIEW View`, then one `INVARIANTS` and one `PROPERTIES` list. Run `bin/dev formal --write`;
   every property must pass and `outcomes.json` appears.
4. **Prove each key property can fail.** For the costliest properties, find the one-line edit that reintroduces the
   bug the property guards (drop a guard, trust a stale value). Add it to the mutation list in
   `tests/workflow/formal.test.ts`, which applies it to a scratch copy and expects TLC to name that property and print
   a trace. Document each edit and its expected failure in the subsystem skill.
5. **Map the model to the code** in `map.json`: `{ "model": "formal/<subsystem>", "actions": [...], "rules": [...],
   "properties": [...] }`, each entry `{ "name", "code": [{ "file", "function" }], "ids": [...] }`. `bin/dev formal`
   fails when a mapped file or function is gone, a name is not defined in the model, an action in `Next` or a checked
   property is unmapped, or an id is unknown (`REQ-*` in the requirement JSON, others as `## <id>,` headings in
   `decisions.md`).
6. **Add the conformance test.** It reads `outcomes.json` and runs every row against the real operations on Postgres,
   seeding through `tests/support/fixture.mts`, and asserts the code's allow or refuse equals the row. One test must
   fail on a row kind it does not run. Name tests `INV-<area>: ...`. Classify only the subsystem's own refusal errors
   as "refuse" and rethrow anything else, so a broken setup fails instead of passing as a refusal. Check the
   statement census for the operations it calls (`.agents/skills/test-standard/SKILL.md`, part 4).
7. **Wire it into the one command and CI.** `bin/dev formal` already finds the model and map. Add the subsystem's
   property names to `tests/workflow/formal.test.ts`, which runs in `pnpm test:workflow` (the required `ci` tooling
   job). Put the conformance test under a glob in `tests/integration/writes/suites.json` so the domain census runs it.
   Add the new paths to the `formal checks` rule in `tools/ci/select.ts`. A change under `.github/` goes through the
   `workflow-gates` owner gate; avoid one when an existing job can run the check.
8. **Write the subsystem skill** at `.agents/skills/formal-<subsystem>/SKILL.md` with: scope (and what is not
   modeled), how to run, the lettered properties, the demonstrations, the conformance test, and a pointer to
   `.agents/skills/maintain-formal-verification/SKILL.md`. Add it to the `AGENTS.md` need table.

If TLC or the conformance test finds a real code weakness, file an evf task for it and continue: do not fix or
describe it in committed text (`.agents/skills/maintain-formal-verification/SKILL.md`, "A real weakness").
