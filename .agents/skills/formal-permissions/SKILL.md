## What the model covers

- **Roles** `owner | admin | member` (`packages/contracts/src/common/values.ts`).
- **Seats in two workspaces**, `w1` and `w2`, each with its founding Owner (`o1`, `o2`). `x` starts as an Admin of
  `w1` and `y` with no seat; invitations seat either in either workspace. An account holds one live seat at a time
  (`seat_uq_0`) and up to two over a run, so a removed account can join again.
- **Sessions that end**: each account has up to two sessions; any may end, and a removal ends every session of the
  removed account (`revoke_removed_seat_sessions`).
- **Seat actions** `appointAdmin`, `demote`, `changeOrdinaryRole` and `remove` (`seats.ts` `mutation`, behind
  `writeAsAdministrator`), checked against the actor's live seat when the action commits. Revisions rise with each
  change, bounded at 3.
- **Invitations**: create (`invite`), revoke (`change`), expiry after 30 days (`current`) and accept (`accept`).
- **Reads and writes that resolve the actor first and run their statement later**: `Resolve` records the actor's
  session, seat, role and revision (`RequestActor.resolve`); any steps may follow; `Run` runs the statement, which
  checks live access itself (`liveRead`, `writeAuthority`; C13, D70). Kinds: `read` (any seat), `adminRead`
  (Owner or Admin, such as the invitation list) and `write` (Owner or Admin when resolved, then the same seat, role and
  revision when it runs). The writes that check access in their final statement through `writeAuthority` are People's
  single-statement writes, which need an Owner or Admin (`seated` in `packages/domain/src/people/core.ts`); the replay
  found the model had let a Member resolve one.

Not modeled: lifecycle witnesses (deletion holds), `pending_domain` accounts, organization kinds, residency links and
affiliations, idempotent replays, resend, lock waits (seat actions are atomic, as their locks make them), and the
~130 callers of the access helpers. `tests/integration/access/tenancy.test.mts` keeps covering every domain read.

## Properties

TLC checks each one on every run (`MCPermissions.cfg`); `map.json` names the code and ids.

| | Property | Kind | Says |
|---|---|---|---|
| a | `OneLiveOwner` | invariant | A workspace never has more than one live owner |
| a | `OwnerSeatFixed` | action | No step changes or removes an owner seat |
| a | `NoInvitationGrantsOwner` | invariant | No invitation names owner, and every owner seat is a founding seat |
| b | `OnlyAdministratorsChangeSeats` | action | A seat changes only by a seat action of a live Owner or Admin seat in its workspace, on a live session |
| b | `NoActionOnEndedSeat` | action | An ended seat never changes, and no seat action targets one |
| c | `TenantAccessNeedsSeat` | action | A read or write in workspace A succeeds only for an actor with a live seat in A |
| d | `StatementSeesLiveAccess` | action | A statement that succeeds ran while its session and seat were live and its role still granted it |
| d | `NoChangeWithoutAccess` | action | Tenant data changes only by a write whose access held when it ran |
| e | `InvitationAcceptedOnce` | action | An accepted invitation never changes again |
| e | `AcceptOnlyPending` | action | Acceptance only from pending: never after expiry or revocation |
| e | `OneSeatPerAcceptance` | invariant | Each accepted invitation made exactly one seat, for its recipient, in its workspace |
| | `TypeOK`, `OneLiveSeatPerAccount` | invariant | Shapes, and `seat_uq_0` |

## Run it

```sh
bin/dev formal            # TLC on every model, outcomes.json and the map check; exits 1 on any failure
bin/dev formal --write    # the same, and rewrites outcomes.json after a deliberate model change
```

It downloads `tla2tools.jar` 1.7.4 once into `~/.cache/everyfield/formal/` and verifies its sha256 on every run. It
uses a local Java 11+ (GitHub's ubuntu runners have one) or else the pinned `eclipse-temurin:21-jre` image through
Docker, so this Mac needs no Java. It prints each property as passed with the distinct states TLC explored (407,808
on 2026-11-15, about 10 s on two cores), or the failed property and TLC's counterexample trace. It then generates the
random behaviors and checks `traces.json` (below); the whole command takes about 15 s on this Mac through Docker.

## Demonstrations: each guard matters

Both run in `tests/workflow/formal.test.ts` on a scratch copy. To see one by hand, make the edit in
`formal/permissions/Permissions.tla`, run `bin/dev formal`, read the trace, then `git checkout formal/permissions`.

1. **The C13 bug class.** A read trusts the session its request resolved at the start. Replace
   `ReadAdmits(q, cur, session) == LiveCheck(q, cur, session)` with
   `ReadAdmits(q, cur, session) == LiveCheck(q, cur, "live")`. TLC fails `StatementSeesLiveAccess` (d): the trace
   resolves a read, ends the session, then runs the read, which returns data. The seat check stays, so no other
   property fails and the multi-worker check always reports this one.
2. **An Admin acts on the Owner seat.** Delete the line `/\ targetRole # "owner"` from `MayChangeSeat`. TLC fails
   `OwnerSeatFixed` (a): the trace has an Admin or the Owner change or remove the owner seat.

## Conformance test

`tests/integration/access/formal-permissions.test.mts` reads `outcomes.json` and runs each of its 93 rows against the
real operations on Postgres, seeded through `tests/support/fixture.mts`, asserting the code's allow or refuse equals
the model's:

- `seat`: each seat action for every (actor role, target role) pair, with the Owner acting on its own seat;
- `invite`: every (inviter role, invited role), owner included, which the contract refuses;
- `revoke`: every actor role;
- `accept`: pending, accepted, revoked and expired invitations of each role, by a seatless and a seated account;
- `statement`: `seats.list` (read) and `invitations.list` (admin read) by each role after no change, a session end,
  a seat removal, a demotion or a promotion that happens after the request resolved its actor.

Change the model alone and `bin/dev formal` reports `outcomes.json` stale; change the code alone and a row fails.
Run it from `packages/domain` on a throwaway Postgres:
`npx tsx --conditions=react-server --test ../../tests/integration/access/formal-permissions.test.mts`.
CI runs it in the domain census (`tests/integration/writes/suites.json`).

## Trace replay

The conformance test checks one step at a time. The replay checks whole behaviors, interleaved as TLC picks them.

**The traces.** `bin/dev formal` runs TLC in simulation mode on the model: 40 behaviors of up to 30 states, from seed
399, on one worker, so the same model always gives the same file. The count, depth, seed and the actions they must
cover are set in one place, `SIMULATIONS` in `tools/formal/formal.ts`. A behavior ends early once no action is
enabled, usually when every session has ended. Each step in `traces.json` names its model action, the action's
arguments (`Run` also its `ok`) and every state entry the step changed; `init` is the shared starting state. The
command fails, naming `formal/permissions/traces.json`, when the committed file differs from what the model generates
(`--write` rewrites it), and it fails, naming what is missing, when the behaviors leave out any action of `Next`, any
seat change (`appointAdmin`, `demote`, `changeOrdinaryRole` to admin and to member, `remove`) or any statement kind
admitted and refused. It prints how many traces and steps it generated and what they cover. TLC 1.7.4 prints each
state through a generated wrapper module that checks nothing else (`simulation` in `formal.ts`, ruling D-1583).

**The replay test** (`tests/integration/access/formal-replay.test.mts`) seeds the starting state for each behavior
through `tests/support/fixture.mts` (two plants with owners `o1` and `o2`, `x` an Admin of `w1`, `y` with no seat, each
with one live session and a password) and runs every step through the operation `map.json` names:

| Action | Real operation |
|---|---|
| `SignIn`, `EndSession` | the identity service's `sign-in/email` and `sign-out` (`handle`) |
| `SeatAction` | the seat service's `appointAdmin`, `demote`, `changeOrdinaryRole`, `remove` |
| `Invite`, `Revoke`, `Accept` | the invitation service's `invite`, `revoke`, `accept` |
| `Expire` | the invitation's dates move back 30 days through the admin pool, so `current` sees it expired |
| `Resolve` | `RequestActor.resolve` on the step's session |
| `Run` | `seats.list` (read), `invitations.list` (admin read), `people.createPerson` through `withPeopleWrite` (write) |

After every step it compares, field by field, the code's result (allowed, or for `Run` admitted or refused as `ok`
says) and the database with the model: each modeled seat's live or ended state, workspace, role and whether its
revision changed; each modeled session's live or ended state; seats and live sessions the model does not have; the
invitation's state; and whether each workspace's tenant data changed. The first difference stops that behavior and
fails with the behavior, the seed, the step, the action and its arguments, model and code side by side, and the steps
so far. A step whose action has no handler fails and names it.

Run it from `packages/domain` on a throwaway Postgres:
`npx tsx --conditions=react-server --test ../../tests/integration/access/formal-replay.test.mts` (about 12 s). CI runs it
in the domain census with the conformance test.

**A fresh seed.** Generate behaviors from a new seed into a directory outside the repository, then replay them:

```sh
bin/dev formal --traces /tmp/permissions-traces            # a random seed, printed
bin/dev formal --traces /tmp/permissions-traces --seed 42  # a given seed: the same behaviors every time
cd packages/domain && FORMAL_TRACES=/tmp/permissions-traces \
  npx tsx --conditions=react-server --test ../../tests/integration/access/formal-replay.test.mts
```

A failure prints the seed, so the same behaviors can be generated and replayed again.

**Demonstrations.** Each was run on 2026-11-15; revert the edit afterwards.

1. **The code skips the live-session check.** In `liveRead` (`packages/domain/src/access/session.ts`), read the account
   from the request's seat instead of `live_session(...)`. The replay fails at the first `Run` after the resolving
   session ended: the model refuses it, the code admits it (seed 399: behavior 1, step 10, an admin read after
   `EndSession o2/1`).
2. **The model stops ending a removed account's sessions.** In `SeatAction`, replace the `sessions' = IF op = "remove"
   ...` expression with `sessions' = sessions`, then `bin/dev formal --write`. TLC still passes every property, and the
   replay fails at the removal step: the model keeps the removed account's session live, the code ended it (seed 399:
   behavior 1, step 3). Revert with `git checkout formal/permissions`.

## Nightly

**What runs.** The `formal` job of GitHub's Nightly workflow (`.github/workflows/nightly.yml`, T-401) runs
`node scripts/nightly-formal.ts` each night and on a manual dispatch, on its own throwaway `pgvector/pgvector:0.8.7-pg18`
service after `pnpm db:migrate`. It prints a fresh random seed and the commit before anything else, generates with
`bin/dev formal --traces $RUNNER_TEMP/nightly-formal/traces --seed <seed>`, prints the trace and step counts and any
model action the seed's traces leave out, and replays them with `FORMAL_TRACES` pointing at that directory. A gap in
coverage is noted, never failed, and the traces still replay (D-1589); there is no retry with another seed. The same
lines go to the job summary. Seed 399 takes about 30 s on this Mac (15 s of TLC through Docker, 13 s of replay).

**Where a failure is filed.** A disagreement, a failed generation, an unreachable database, a crashed replay or one
with no test fails the step with one `::error::` line that says which, the seed, the commit and the commands that
reproduce it. On main, fail-forward opens or updates the one Nightly incident for the failed run, and its log excerpt
ends at that first `##[error]` line, so the incident carries the seed (D-1587). No other issue writer exists.

**Why no detail is printed.** The repository, its Actions logs and its artifacts are public, and a disagreement can be
a real weakness. The replay's own output (the behavior, the action and its arguments, model and code state) goes only
to `$RUNNER_TEMP/nightly-formal/replay.log`, which no step prints or uploads (D-1588).

**Reproduce a filed seed.** Run the commands in the incident: check out its commit, then

```sh
bin/dev formal --traces /tmp/formal-seed-<seed> --seed <seed>
cd packages/domain && FORMAL_TRACES=/tmp/formal-seed-<seed> \
  npx tsx --conditions=react-server --test ../../tests/integration/access/formal-replay.test.mts
```

on a throwaway Postgres (`.agents/skills/verify/SKILL.md`). Or run the whole nightly step locally with
`node scripts/nightly-formal.ts --seed <seed>` against `DATABASE_URL` on a throwaway `everyfield_ci` (with `CI=true` and
`EARLY_ACCESS_TEST_DATABASE=1`, after `pnpm db:migrate`); it prints where its `replay.log` is. Then follow
`.agents/skills/maintain-formal-verification/SKILL.md` ("A filed nightly seed").
